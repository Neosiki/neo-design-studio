# Camera Language · 카메라 무빙 연출 체계

> **이 파일을 언제 읽는가**: 화면에 「샷 단위」 움직임이 나오기 전에 — zoom / pan / orbit / parallax /
> 전환 / 정경·마무리, 움직이는 게 「요소」가 아니라 「카메라」라면 timeline을 쓰기 전에 여기를 먼저 읽는다.
> 요소가 어떻게 움직이는지(등장/stagger/물리감)는 `animation-best-practices.md`가 맡는다.
> 이 파일이 답하는 건 **카메라가 언제 움직이고, 얼마나 크게, 얼마나 오래 움직이며, 샷과 샷을 어떻게 잇는가**다.
> GSAP 쪽의 실행 가능한 구현(rig 컨테이너, PageCam 변환, 로그 시간 helper)은
> `gsap-recipes.md`의 「Camera Rig 레시피」 절을 본다. 이 문서는 디자인 판단과 공식만 준다.
>
> 파라미터 출처 표기 규약: **(HuaRec)** = 화록 Studio 카메라 무빙 연출 시스템의 실측 파라미터,
> **(shotcraft)** = video-shotcraft의 106카드 샷 체계, **(실측)** = 이 skill 프로젝트의 실전,
> **(추정)** = 일반 영화 어휘에서 가져온 것으로, 파라미터는 실측 보정이 필요하다.

## §0 · 논지 · 카메라 무빙은 예산제이고 특효약이 아니다

AI가 만든 애니메이션 대부분의 카메라 무빙은 「특효약」 사고다. zoom을 넣을 수 있는 곳에는 다 넣고,
카메라가 많이 움직이면 더 「고급」이라고 여긴다.
이게 어지러움과 싸구려 느낌의 공통 출처다. 올바른 심상 모형은 두 공리에서 나온다 (HuaRec):

- **A1 가시성 불변량**: 어느 순간이든 관객이 봐야 할 것은 가시 영역 안에 있어야 한다(8% 안전 여백 포함).
  이를 어기는 샷은 배율을 낮추거나, 합치거나, 아니면 찍지 않는다.
- **A2 편안함 예산**: 카메라가 변할 때마다 주의력을 한 번 소비하는 것이므로 예산으로 관리해야 한다.
  예산을 다 썼으면 아무리 좋은 샷도 찍지 않는다.

| 예산 항목 | 대표값 | 조절 감각 |
|---|---|---|
| 인접 샷 변화 간격 | ≥2.6-3.0s(절제 등급 5.0s) | 2.6s보다 짧으면 관객이 어지러워한다. MTV식 빠른 컷은 제품 데모에 맞지 않는다 (HuaRec) |
| 15s 구간 안의 샷 변화 | ≤4-5회(절제 등급 3회) | 넘으면 동기가 가장 약한 샷을 자른다. 간격을 압축하는 게 아니다 (HuaRec) |
| 밀어 들어가는 배율 하한 | 1.25x | 1.25x보다 낮은 zoom은 시각 변화가 인지되지 않고 그냥 흔들림이라 찍지 않는다(정경 1.06x만 유일한 예외) (HuaRec) |
| 밀어 들어가는 배율 상한 | 2.3x(절제 등급 1.8x) | 더 높이면 픽셀 밀도가 버티지 못한다. 소재를 먼저 바꾸고 나서 배율을 논한다 (HuaRec) |
| 분당 샷 수 | 절제는 분당 ≤4샷, 일반은 분당 ≤6샷 | 「숨을 남긴다, MTV가 아니다」 (HuaRec) |

여기에 스타일 공리 두 개를 겹친다 (shotcraft):

1. **영화감 = 카메라 무빙 × 빛과 그림자 × 리듬 × 소리이고, 기교를 부린 애니메이션이 아니다**. 네 차원이 각각 합격하는 게 한 차원만 끝까지 올리는 것보다 낫다.
2. **리듬 선호는 한 방향이다: 느린 게 빠른 것보다 낫다**. 지금까지 받은 사용자 피드백은 전부 「느리게, 머물러」를 가리켰고 「빠르게」를 가리킨 건 하나도 없다.
   길이가 애매하면 긴 쪽을 고른다. 카메라를 움직일지 애매하면 움직이지 않는 쪽을 고른다.

이 두 가지는 best-practices §0.2의 「관객에게 양보한다」와 같은 뿌리다. 카메라는 관객의 눈을 대신해
결정을 내리는 것이고, 그 결정이 적고 정확할수록 관객은 나를 더 신뢰한다.

## §1 · 샷 어휘표 · 카메라 무빙 동기 결정표

모든 샷 동작은 먼저 동기를 묻는다: **이 샷은 관객을 대신해 어떤 질문에 답했는가?** 답하지 못하면 움직이지 않는다.

| 샷 | 동기(언제 주는가) | 파라미터 구간 | 금기 |
|---|---|---|---|
| **push in 밀어 들어가기** | 「다음은 여기를 본다」: 구체적인 UI 요소·데이터·핵심어에 초점을 맞춘다. 긴장도를 올린다 | 배율 1.3 / 1.45 / 1.8 / 2.3 등급(§4 참고), 길이는 로그 공식을 따른다. 0.15s 먼저 샷이 들어간다 (HuaRec) | 1.25x 미만은 밀지 않는다. 스크롤·페이지 전환·영상 재생처럼 전체 화면이 변하는 동안에는 밀지 않는다(「스크롤할 때 밀어 들어가면 어지럽다」). 내레이션 중간에는 카메라를 움직이지 않는다(§6 move on pause 참고) (HuaRec) |
| **pull out 빼기** | 전체와 맥락을 드러낸다: 「알고 보니 더 큰 체계의 일부였다」. 마무리 인사 | 길이는 같은 로그 공식. 마무리로 빼기 0.55s + 전경에서 ≥0.8s 정지 (HuaRec) | 「빼기-넣기-빼기」 펌핑을 금한다. 샷 사이 틈이 전환 시간보다 짧으면 바로 다음 샷으로 잇고 1x로 돌아가지 않는다(§5 참고) (HuaRec) |
| **pan 팬** | 중간 거리에 있는 두 초점 사이를 옮긴다(정규화 거리 0.22-0.45). 한 샷으로 나란히 놓인 여러 요소를 훑는다 | 합산 배율이 ≥1.25는 돼야 팬할 값이 있다. 대각선 팬은 이중 주파수 사인을 쓴다(X/Y 주파수비 0.22:0.35, 진폭 30-40px) (HuaRec / 이 skill의 기존 규칙) | 초점 거리가 >0.45면 팬하지 않고(대각선으로 튄다) 샷을 버린다. 순수한 단일 축 팬은 기계적이라 대각선을 우선한다 |
| **orbit 오비트** | 주인공 하나의 질감을 클로즈업한다. 「실체감」이 가장 강한 샷이고, hero 요소의 전기를 써 준다 | rotY 주도 + persp 1100-1200px. 실측 카메라 위치는 rotX46/rotY−30/rotZ9 → rotX42/rotY26/rotZ−7 (shotcraft) | 한 수법은 전편에서 한 번만 주인공으로 쓴다 (shotcraft). 정보가 밀집한 화면에는 쓰지 않는다(카메라 위치는 가독성에 봉사한다. 글자가 많으면 정면으로 본다) |
| **dolly zoom** | 「세계관이 뒤집히는」 폭로의 순간: 주체는 그대로인데 맥락이```html
<div id="viewport">          <!-- 고정 뷰포트, overflow: hidden, perspective를 들고 있다 -->
  <div id="camera">          <!-- 카메라 층: 카메라 transform만 지고, 나머지는 아무것도 하지 않는다 -->
    <div id="world">         <!-- 월드 층: 화면의 모든 내용이 여기 살고, 요소 애니메이션은 world 내부만 움직인다 -->
      ...장면 내용...
    </div>
  </div>
  <div id="hud">             <!-- 자막 / 코너 표시 / chrome: #camera와 같은 층이라 자연히 카메라를 따라가지 않는다 -->
  </div>
</div>
```

역할 분담의 철칙:

- `#camera`에는 카메라 tween만 나온다(translate / scale / rotate / zoom 속성). 요소 등장, stagger,
  hover 상태는 전부 `#world` 내부 요소에 쓴다. 두 층은 서로를 모르기에, 카메라는 언제든 전체를 다시 짜도 요소 애니메이션을 건드리지 않는다
- 자막과 chrome은 **`#hud`에 두는 걸 우선한다**. 비용 없이 정지 상태를 유지한다. 「world 안의 어떤 요소를 반드시 따라가야 하지만
  글자 크기는 일정해야 하는」 표시(따라다니는 tooltip 같은 것)만 그 요소에 counter-transform을 넣는다:
  `scale(1/zoom)`으로 카메라 확대를 반대로 상쇄하고, 매 프레임 카메라와 동기화해 갱신한다
- **transform-origin이 곧 밀어 들어갈 목표점이다**: 평면 zoom은 origin을 목표 요소의 중심에 두고 scale하면
  「카메라가 그것을 겨누고 밀어 들어간다」와 같아진다. PageCam 모드에서는 cx/cy가 같은 역할을 맡는다

### 3.2 PageCam 키프레임 모형(shotcraft, 2.5D 카메라 수학)

카메라 상태를 키프레임 객체로 정의하면, 카메라 움직임 = 키프레임 사이의 보간이 된다:

```
{ frame, cx, cy, zoom, rotX, rotY, rotZ, persp }
```

cx/cy는 **월드 좌표계에서 카메라가 겨누는 점**이고 zoom은 배율이다. 1920×1080 캔버스를 예로 들면
(다른 크기에서는 960/540을 W/2, H/2로 바꾼다):

**평면 모드**(회전 없이 순수 zoom + pan):

```
transform: translate(960 − cx·zoom, 540 − cy·zoom) scale(zoom)
transform-origin: 0 0
```

**3D 모드**(rotX/rotY/rotZ가 있을 때):

```
바깥층(#camera): perspective: persp·zoom;  perspective-origin: 960px 540px
안쪽층(#world):  zoom: {zoom};                        /* CSS zoom 속성이다. §3.4 참고 */
                Tx = 960/zoom − cx;  Ty = 540/zoom − cy
                transform: translate(Tx, Ty) rotateY() rotateX() rotateZ()
                transform-origin: cx cy
                transform-style: preserve-3d
```

대표적인 카메라 위치 파라미터 (shotcraft 실측): 전체 페이지 zoom 0.78 → 클로즈업 2.6.
측면 촬영 rotY34 / rotX8 / persp1200(측면이 부감보다 낫다. rotY 주도 + rotX는 조금만).
orbit의 시작·끝 위치는 §1 표를 본다.

### 3.3 rig 시공 주의(카메라 전용 함정)

- **pan에서 가장자리가 드러나는 것**: `#world`는 뷰포트보다 커야 한다(사방으로 bleed ≥ 최대 pan 진폭 + 8% 여백).
  그러지 않으면 팬할 때 캔버스 밖의 빈 공간이 드러난다. 이건 A1 가시성 공리의 반대면이다. 봐서는 안 될 것도 보이면 안 된다
- **perspective가 끊기는 것**: `#camera`와 `#world` 사이의 어떤 중간 층에든
  `overflow: hidden`, `filter`, `opacity <1`이 붙으면 새 stacking context가 생겨
  preserve-3d가 죽고 3D 층 구조가 순식간에 평평해진다. 3D 모드에서 필터 효과는 가장 안쪽 요소에만 넣는다
- **프레임 단위 이탈 방지** (HuaRec): 카메라 초점이 움직이는 점을 따라갈 때, 매 프레임 목표가 가시 영역을 벗어났는지 확인한다.
  벗어났으면 배율은 유지하고 벗어난 축으로만 최소한으로 보정해 경계로 끌어온다. 카메라가 「한 발 양보」하는 게 낫고, 목표가 화면을 벗어나는 건 안 된다

### 3.4 CSS zoom 래스터화 기법 · 3D 글자 흐려짐을 근본에서 잡는다(문서 전체에서 가장 값비싼 지식, shotcraft)

**문제**: 3D 모드에서 `transform: scale()`로 페이지를 확대하면, Chromium은 요소의 레이아웃 크기대로 래스터화한 다음
그 비트맵을 확대하므로 글자가 반드시 흐려진다. 배율이 높을수록 더 심해지고, 2x 이상은 전달할 수 없다.

**해법**: 확대를 `transform: scale`로 하지 않고 **CSS `zoom` 속성**으로 한다. `zoom`은 레이아웃 단위 확대라서
Chromium이 확대된 크기로 다시 layout하고 래스터화하므로, 어떤 배율에서도 글자가 벡터급으로 선명하다.
§3.2의 3D 모드 공식에서 안쪽층에 `scale({zoom})`이 아니라 `zoom: {zoom}`을 쓴 게 바로 이 때문이다.

함께 챙길 점:

| 요점 | 방법 | 출처 |
|---|---|---|
| 좌표 보정 | `zoom`이 레이아웃 좌표계를 바꾸므로 translate 값을 zoom으로 나눠야 한다: `Tx = 960/zoom − cx`(§3.2 공식에 이미 들어 있다) | (shotcraft) |
| reflow 금지 규칙과의 관계 | gsap-recipes §6.2가 레이아웃 속성을 tween하지 말라고 하는 건 정수 snap 떨림 때문이다. `zoom`은 페이지 전체 단위 확대라 snap 양을 감지할 수 없고, 글자가 선명해지는 이득이 훨씬 크다. **이 기법은 §6.2의 유일한 합법적 예외이고, `#world` 카메라 층에만 쓴다** | (실측) |
| 렌더링 환경 | HyperFrames / Playwright의 오프라인 프레임별 seek 렌더링에 완전히 적용된다. 매 프레임 다시 layout하는 시간은 산출물에 영향이 없고 렌더 시간만 늘린다. 실시간 브라우저 preview에서 프레임이 떨어지는 건 정상이니 렌더 산출물을 기준으로 본다 | (shotcraft) |
| 비트맵 소재 보강 | 전체 페이지 스크린샷은 2x로 샘플링한다. 클로즈업 요소는 4x로 따로 찍어 두고, 밀어 들어가는 동안 6f 크로스 페이드로 낮은 배율 텍스처를 덮는다 | (shotcraft) |
| 피사계 심도 분위기 | DoF는 분위기용으로만 쓴다. 상단 그라데이션 띠에 blur + mask를 걸고, 층마다 실제 심도를 계산하지는 않는다 | (shotcraft) |

## §4 · 카메라 이징과 길이

### 4.1 이징 어휘

| 상황 | easing | 조절 감각 |
|---|---|---|
| 능동적인 카메라 무빙(밀기·빼기, 시작점과 끝점이 분명하다) | `cubic-bezier(0.65,0,0.35,1)` = GSAP `power3.inOut` | 양 끝이 다 안정적이고 「연출자가 샷을 준다」는 느낌이 난다. **절대 선형으로 하지 않고, 절대 스프링으로 넘기지 않는다** (HuaRec) |
| 따라가는 카메라 무빙(이미 시작된 동작을 카메라가 쫓는다) | `cubic-bezier(0.33,0,0.15,1)` | 출발은 가볍고 제동은 아주 길어서, 카메라가 「끊어 넘어가는」 게 아니라 「따라 올라가는」 것처럼 보인다. shotcraft 카메라의 기본값 |
| 계속되는 표류(idle drift, 등속 순람) | `sine.inOut` yoyo 또는 `none` | 카메라 등속을 허용하는 유일한 상황이다(gsap-recipes §1의 기존 규칙). 시작점과 끝점이 있는 동작에는 쓰지 않는다 |
| 커서·초점 추종 스무딩 | `quickTo` + 약 0.15s 스무딩. 경로 보간은 Catmull-Rom | 순방향 + 역방향 EMA의 영위상 발상이다. 바짝 따라가되 떨지 않는다 (HuaRec) |

두 기본값이 충돌할 때의 판정: 한 번의 밀기·빼기는 HuaRec을 따르고(power3.inOut),
복합 이동과 여러 구간이 이어지는 샷은 shotcraft를 따른다(0.33,0,0.15,1).

### 4.2 zoom 길이 로그 공식(고정 duration은 아마추어 느낌의 출처다)

모든 밀기·빼기 길이는 배율 변화량으로 정해서, 어떤 폭의 zoom이든 「시각 속도」가 일정하도록 보장한다:

```
duration = 0.55 × |ln(zoom₂ / zoom₁)| / ln 2      clamp to [0.30, 0.94] 초
```

1→2x로 밀면 정확히 0.55s, 1→1.3x는 약 0.30s(하한에 닿는다), 0.78→2.6x는 상한 0.94s에 닿는다. (HuaRec)
화면 크기 차이가 큰 전환은 더 오래, 작은 전환은 더 짧게 해서 「단번에 튀어 들어가는 것」과 「늘어지는 것」을 함께 막는다.

### 4.3 zoom 등급표

| 등급 | 배율 | 용도 | 조절 감각 |
|---|---|---|---|
| 정경 미세 밀기 | 1.06x | 오프닝 정경에만 쓴다(§6). 관객은 zoom을 감지하지 못하고 「화면이 살아 있다」만 감지한다 | 1.25x 미만을 허용하는 유일한 등급 (HuaRec) |
| 약하게 밀기 | 1.3x | 힌트 수준의 초점: 전체 읽기를 끊지 않고 「이 부근을 보라」고만 한다 | |
| 중간 밀기 | 1.45x | 표준 UI 클로즈업: 패널 하나 / 코드 한 토막 | |
| 세게 밀기 | 1.8x | 단일 요소 클로즈업: 버튼 하나 / 숫자 하나 | 절제 등급의 상한 (HuaRec) |
| 상한 | 2.3x | 극단적 클로즈업. 소재가 반드시 버텨야 한다(2x 스크린샷 / 4x 조각, §3.4) | 넘으면 소재를 바꾸고 억지로 밀지 않는다 (HuaRec) |

화면 잡는 공식 (HuaRec): `scale = 0.8 / max(목표 바운딩 박스의 정규화 폭, 높이)`, 그다음 등급 구간으로 조인다.
내용이 가시 영역의 80%를 차지하고 20%를 숨으로 남긴다. 꽉 채우지 않는다.

### 4.4 리듬 예산(§0 예산표와 연동)

- 인접 샷 변화 간격 ≥2.6-3.0s, 15s 구간에 ≤4-5회 (HuaRec)
- 동작 0.15s 전에 샷이 들어간다(카메라가 먼저 도착하고 동작이 나중에 일어난다). 동작이 끝나면 1.2s 머문 뒤 움직인다 (HuaRec)
- 길이가 1.2s 미만인 고립된 작은 동작에는 따로 샷을 줄 값이 없다. 「한 번 누를 때마다 한 번 펌프질하는」 것을 막는다 (HuaRec)

## §5 · 샷 사이 문법 · 어지럼 방지의 핵심

**어지럼은 개별 샷이 만드는 게 아니라 샷과 샷을 잇는 방식이 만든다.** 「빼기-넣기-빼기」 펌핑과
먼 초점 사이를 계속 튀는 것이 어지럼의 대부분을 만들어 낸다 (HuaRec). 인접한 두 샷(간격 <1.5s)은 초점 거리로 셋으로 나눈다:

| 초점 정규화 거리 | 잇는 방법 | 설명 |
|---|---|---|
| <0.22(가깝다) | **샷 합치기** | 한 샷으로 합친다. 두 목표의 합산 바운딩 박스로 배율을 다시 계산하고 한 샷에서 다 본다 |
| 0.22-0.45(중간) | **팬으로 바꾸기** | 배율을 좀 넓게 잡는 게 낫다(합산 배율 ≥1.25). 한 샷으로 팬해서 넘어가고 「뺐다가 다시 넣지」 않는다 |
| >0.45(멀다·대각선) | **샷 버리기** | 동기가 더 약한 샷을 자른다. **먼 초점 두 개를 연달아 찍는 건 절대 하지 않는다.** 대각선으로 튀는 게 가장 어지러운 이음법이다 |

시간 순서 규칙 두 개를 더한다 (HuaRec):

- **틈이 짧으면 바로 잇는다**: 인접 샷의 틈이 전환 시간보다 짧으면 1.0x로 돌아가지 않고, 현재 배율에서
  바로 다음 샷의 배율과 초점으로 전환한다. 1x로 돌아갔다가 다시 미는 게 「펌핑 느낌」의 직접적인 출처다
- **틈이 ≥1.5s일 때만 「뺐다가 다시 밀기」를 허용한다**: 관객이 전경에서 다시 위치를 잡을 시간이 충분해야 빼고 넣어도 어지럽지 않다

## §6 · 영화적 개막과 폐막 · 정경, 마무리, move on pause

이 세 문법은 비용이 아주 낮은데 작품 느낌은 뚜렷하게 올려 준다 (HuaRec):

1. **정경(establishing shot)**: 길이가 >14s이고 첫 정식 샷이 7s 뒤에 온다면,
   오프닝에 [0, 3.0s] 구간의 **1.06x 중심 미세 밀기**를 넣는다. 시작할 때 이미 살짝 밀린 상태이고 3초 안에 천천히 전경으로 돌아온다.
   관객의 첫 느낌이 「PPT가 재생되기 시작했다」가 아니라 「카메라가 살아 있다」가 된다
2. **전경 마무리 철칙**: 마지막 샷은 미리 정리해서, 빼는 전환 0.55s + **전경에서 ≥0.8s 정지**를 남긴다.
   완성본은 언제나 전경 정지로 끝내고, **밀린 상태에서 뚝 끊지 않는다**. best-practices의 「뚝 끊고 + hold」
   마무리와 완전히 호환된다. hold하는 그 한 프레임이 반드시 전경이어야 한다
3. **Move on pause**: cut on action, move on pause. 내레이션이 있는 애니메이션에서 카메라 이동이
   말하는 중간에 부딪히면, 가장 가까운 음성 무음 지점으로 앞쪽으로 붙인다(최대 0.8s 앞으로, **앞으로만 옮기고 뒤로 밀지 않는다**).
   관객이 청각이 비는 틈에 시선을 옮기는 게 인지 비용이 가장 낮다. 해설 pipeline(voiceover-pipeline.md)에서 샷을 배치할 때는
   narration의 문장 사이 틈을 그대로 붙일 지점으로 쓴다

## §7 · 전환 문법표 · 세 층의 어휘

전환은 독립된 층이다. 이음매는 **에너지 낙차**로 고르고, 한 이음매에는 한 가지만 쓰며, 전환 프레임은 인접 샷의 예산에서 떼어 온다.
「좋다고 인정받는 발표 영상은 전편에 맨 컷이 한 번도 없다」 (shotcraft).

### 7.1 shot-transitions 여섯 가지(존재감이 있는 전환, 에너지 낙차가 큰 이음매에 쓴다)

| 방식 | 맞는 에너지 낙차 | 파라미터 | 함정 |
|---|---|---|---|
| 흐르는 흰 화면 flash-wash | 높음→높음, 단락을 강하게 전환 | 흰 화면 2-4f 피크, 양쪽에 각각 5f 그라데이션 | 흰 섬광은 컷 지점만 덮는다. 장식으로 반복해 쓰지 않는다 |
| 어두운 화면 통과 dip-to-dark | 높음→낮음, 감정을 낮춘다 | rgba(20,20,20,0.9) 수준까지 어둡게, 전체 길이 ≤0.6s | 어두운 화면에 머물지 않는다. 관객이 영상이 끝났다고 여긴다 |
| 초점 흐림 이어받기 defocus-handoff | 중간→중간, 같은 급의 화제 전환 | 나가는 샷 blur 0→8px와 들어오는 샷 blur 8px→0을 ≥8f 겹친다 | 넓은 면적의 blur는 ≤24px로 한다(DoF 성능 제약) |
| 검은 화면 타이틀 카드 title-card | 챕터 단위 구분 | 카드 hold ≥1s, 앞뒤로 각각 0.3s 전환 | 전편에 ≤2장. 많으면 슬라이드처럼 보인다 |
| whip-pan 휘두르기 | 낮음→높음, 에너지가 급히 오른다 | 양 끝 hold ≥20f → 8f 동안 1.5화면을 휘두른다. 피크가 ≥300px/f는 돼야 제대로 흐려진다 (shotcraft) | 느리면 그냥 평범한 pan이다. 제대로 흐려지지 않으면 오히려 어설픔이 드러난다 |
| mask-wipe 창 통과 | 공간 이동, 「한 화면을 통과해 다른 화면으로 들어간다」 | 마스크 경계 easing `(0.4,0,0.6,1)` (shotcraft) | 마스크 모양은 반드시 화면에 이미 있는 요소에서 와야 한다(창이나 카드의 둥근 모서리). 근거 없는 모양은 slop이다 |

### 7.2 hidden-cut 세 가지(관객이 컷을 알아채지 못하는 전환)

| 방식 | 방법 | 출처 |
|---|---|---|
| flash-cut 흰 섬광 걸침 | 흰 섬광이 하드 컷 지점에 걸터앉는다. 양쪽에 각각 5f, 컷 지점만 덮는다 | (shotcraft, 실증된 파라미터) |
| 전경 가림 컷 | 전경 요소 하나(카드/패널/커서 손)가 화면 전체를 스치는 순간에 장면을 바꾼다 | (추정: 일반 영화 어휘, 파라미터는 실측 필요) |
| 모션 블러 컷 | 고속 운동의 피크 프레임에서 하드 컷하고, 양쪽 운동 방향을 맞춰 motion blur가 컷 지점을 삼키게 한다 | (추정: 일반 영화 어휘, 파라미터는 실측 필요) |

### 7.3 travel 두 가지(공간이 이어지는 전환, 에너지 낙차 없이 장면이 이동한다)

| 방식 | 방법 | 함정 |
|---|---|---|
| 공유 요소 자리 잡기 | 앞 샷의 어떤 요소(logo/카드)가 끊기지 않고 움직여 뒤 샷에서의 새 자리로 간다. FLIP 발상의 카메라 버전이다 | 요소가 두 샷에서 같은 정체를 가져야 한다. 형태가 너무 많이 변하면 「같은 것」이라는 인지가 끊긴다 |
| 글자 속 빈 공간 통과 | 카메라가 큰 글자의 속 빈 공간(O·ㅇ·0의 구멍)을 통과해 다음 장면으로 들어간다 | 빈 공간 크기가 충분해야 한다(화면 높이의 ≥1/3). 통과 구간의 zoom은 로그 길이의 상한 0.94s로 간다 |

선택 속견표: 에너지 낙차가 크다 → 여섯 가지 중 하나를 고른다. 알아채이고 싶지 않다 → hidden-cut.
두 장면이 공간적으로 이어진다 → travel.
하드 컷은 금지가 아니라 「위 어느 층으로든 포장돼야 한다」는 뜻이다.

## §8 · 다층 parallax 레시피 · 유사 dolly-zoom

### 8.1 parallax 층 속도 계수 (shotcraft)

| 파라미터 | 대표값 | 조절 감각 |
|---|---|---|
| 층 속도 계수 | 원경 0.35 / 중경 0.7 / 근경 1.4(카메라 이동량의 배수) | 인접 층의 속도비가 **2배 이상**은 돼야 구별된다. 1.2배 차이는 관객이 읽어내지 못한다 |
| 층 수 | ≤4층 | 4층을 넘는 시차는 아무도 알아보지 못하고 순수하게 예산만 낭비한다 |
| 구현 | 각 층이 같은 카메라 x/y에 자기 계수를 곱해 translate한다 | 전부 카메라 상태에서 도출되므로 seek-safe다. 층마다 별도 tween을 주지 않는다 |

### 8.2 유사 dolly-zoom(순수 CSS, 진짜 3D가 필요 없다)

```
주체: 못 박아 고정한다(또는 ≤1.02x 숨쉬기만 준다)
배경: scale 1 → 2.0-2.5, 동시에 opacity를 ≤0.6까지 낮춘다
```

주체는 그대로인데 배경이 관객에게 밀려오면서 「세계가 다가오는데 주인공은 굳어 있다」는 반전감이 생긴다 (shotcraft).
길이를 넉넉히 준다(≥1.2s). 용도는 §1을 본다. 전편에서 최대 한 번, 진짜 폭로의 순간에 남겨 둔다.

## §9 · 운동에서 파생되는 신호 · blur / 추종 / 잔진동

카메라의 「속도감」은 duration을 더 짧게 해서 얻는 게 아니라, 속도에서 **파생된** 2차 신호로 얻는다 (shotcraft / HuaRec):

| 신호 | 공식 | 파라미터 |
|---|---|---|
| 속도로 구동하는 blur | `v = velocityAt(f)`(중앙 차분: `(pos(f+1)−pos(f−1))/2`), blur 강도 ∝ v | zoom 속도가 >0.6/s일 때만 발동하고 강도는 `min(10, v×5)`px. **움직이는 순간에만 흐리고 정지 프레임은 언제나 선명하다** (HuaRec) |
| lagged 추종 층 | 추종 층 = 주체를 `f − delay` 지점에서 샘플링한다 | 그림자는 2f 지연, 잔상은 4f 지연 (shotcraft). 잔상은 motion blur의 대체다: 경로 5% 지연 + blur(6px) + opacity 0.25·(1−t) |
| dampedSettle 잔진동 | `e^(−d·t) · sin(2π·f·t)`, f≈0.1, damping≈0.15 | 카메라가 급정지한 뒤의 미세한 잔여 흔들림 1-2회, 진폭 ≤3px. 능동적인 카메라 무빙(§4.1의 inOut 계열)에는 넣지 않고 whip-pan이나 급제동 계열에만 준다 |

세 가지 모두 시간의 순수 함수라서(차분, 지연 샘플링, 닫힌 형태의 감쇠) 자연히 seek-safe이고,
gsap-recipes §6의 결정성 요구를 충족한다.

## §10 · 카메라 무빙 자체 점검 목록(timeline을 쓴 뒤 60초)

- [ ] 모든 샷 동작이 「관객을 대신해 어떤 질문에 답했는가」에 답할 수 있는가? 답하지 못하는 건 지웠는가?
- [ ] 1.25x 미만의 zoom이 없는가(정경 1.06x 제외)?
- [ ] 인접 샷 간격이 ≥2.6s이고 15s 구간에 ≤4-5회인가?
- [ ] 모든 밀기·빼기 길이가 로그 공식을 따르고, 머리로 대충 잡은 고정 duration이 없는가?
- [ ] 밀기·빼기 easing이 power3.inOut이고 linear나 스프링 넘김이 없는가?
- [ ] 인접 샷을 초점 거리로 셋으로 나눠 판정했는가(합치기/팬/버리기)? 먼 초점을 두 번 연달아 튀는 게 없는가?
- [ ] 틈이 짧은 샷은 바로 이었고, 1x로 돌아가는 펌핑이 없는가?
- [ ] 길이가 >14s이고 첫 샷이 7s보다 늦다면, 1.06x 정경 미세 밀기를 넣었는가?
- [ ] 끝이 전경 정지 ≥0.8s이고, 밀린 상태로 끝나지 않는가?
- [ ] 내레이션이 있다면, 카메라 이동을 음성 틈에 붙였는가(앞으로만 ≤0.8s)?
- [ ] 카메라 움직임이 전부 `#camera` 층으로 모였고, 요소 애니메이션과 transform을 다투지 않는가?
- [ ] 3D 글자 클로즈업이 CSS zoom 래스터화를 따랐고, scale 확대로 흐려지지 않았는가?
- [ ] 전환 이음매마다 한 가지만 썼고, 전편에 맨 컷이 없는가?
- [ ] parallax의 인접 층 속도비가 ≥2배이고 층이 ≤4개인가?
- [ ] blur가 운동의 과도 구간에만 나오고 정지 프레임은 전부 선명한가?
