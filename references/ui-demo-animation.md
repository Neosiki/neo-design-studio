# 제품 UI 쇼케이스 애니메이션 Playbook

> **「홍보할 제품에 UI 화면이 있다」면 여기가 유일한 입구다.** 외주 건, 출시 애니메이션, 기능 시연 — 화면의 주인공이 인터페이스라면 이 문서를 먼저 읽고 시작한다.
>
> 핵심 주장 한 문장: **제품 애니메이션의 질감은 특수효과가 아니라 「실제 UI + 영화적 카메라 워크」에서 거의 전부 나온다.** 테크 느낌은 관객이 「저게 바로 그 제품이다」라고 알아보게 만드는 데서, 그리고 카메라가 그것을 어떻게 보는지에서 나온다. 파티클, 글로우, 사이버 그라데이션이 아니다. 진짜 스크린샷 한 장에 절제된 줌인 한 번이 손으로 열 겹 쌓아 만든 가짜 화면보다 낫다.
>
> 파라미터 출처 표기 규칙: (shotcraft·카드명) = video-shotcraft 샷 카드 실측값, (huarec) = 화록 Studio 카메라 연출 시스템, (best-practices §x)(gsap-recipes §x) = 이 skill의 기존 reference. 30fps 기준, 1f ≈ 33ms.
>
> 역할 분담: 이 문서는 「주인공인 UI를 어떻게 연기시키는가」를 다룬다. 샷 어휘와 카메라 워크의 동기는 `camera-language.md`, 요소 단위 모션 문법(easing, stagger, FLIP, Chunk Reveal)은 `animation-best-practices.md`를 본다. 여기서는 인용만 하고 다시 쓰지 않는다.

## §0 두 가지 공리(8식의 모든 파라미터보다 우선한다)

| 공리 | 내용 | 출처 |
|---|---|---|
| **가시성 불변식** | 어느 시점에서든 커서와 지금 벌어지는 UI 조작은 가시 영역 안(8% 안전 여백 포함)에 있어야 한다. 이를 어기는 컷은 배율을 낮추거나, 컷을 합치거나, 아예 찍지 않는다 | huarec A1 |
| **시각 언어는 제품에서 자란다** | 먼저 제품 자신의 디자인 토큰(글꼴/라운딩/색판/그리드)을 뽑아내고, 영상 전체에서는 그것을 재사용하거나 절제해서 확장만 한다. 샷 카드에서 물려받는 것은 모션 문법과 리듬뿐이고, 표피는 대상 제품에 맞춰 다시 씌운다 | shotcraft 공리 1 |

## §1 의사결정 트리: 실제 UI 스크린샷 카메라 워크 vs HTML로 UI 재구축

이 문서에서 **작업량에 가장 크게 영향을 주는 결정**이다. 두 경로는 한 자릿수 차이가 난다. 기본적으로 가장 싼 경로부터 따진다.

```
제품 UI가 등장한다
 │
 ├─ 화면은 「보여지기만」 하면 되는가(줌인/투어/부양/대비)?
 │   └─ 예 → 【경로 1】스크린샷 + 프레임 + 2.5D 카메라 워크. 여기서 끝, 재구축하지 않는다
 │
 ├─ 몇 개 요소만 따로 움직이면 되는가(카드 한 장이 떠오른다, 데이터 한 줄이 스크롤된다)?
 │   └─ 예 → 【경로 3】혼합: 스크린샷을 바탕에 깔고 핵심 요소만 슬라이스로 재구축
 │
 └─ 화면 자체가 서사의 주체이고, 요소가 하나씩 등장/조작에 반응/상태를 바꿔야 하는가?
     └─ 예 → 【경로 2】HTML 재구축. build-up, 8식 ②로 간다
```

| 경로 | 방법 | 작업량 | 적용 기준 |
|---|---|---|---|
| 1 · 스크린샷 카메라 워크 | 실제 스크린샷을 `browser_window.jsx` / `macos_window.jsx` 디바이스 프레임에 넣고, 컨테이너에 zoom/rotate/pan을 준다 | 시간 단위 | 화면이 「관찰 대상」일 때. 관객이 화면 내부의 변화를 볼 필요가 없다 |
| 2 · HTML 재구축 | 스크린샷을 픽셀 단위로 따라가며 움직일 수 있는 DOM 구조로 다시 만든다 | 일 단위 | 요소마다 독립된 타임라인이 필요할 때. 단계적 생성, typing, 상태 전환, hover 반응 |
| 3 · 혼합 | 전체 페이지 스크린샷을 바탕 텍스처로 쓰고, 움직일 요소만 투명 배경 슬라이스로 따내 원래 좌표 위에 겹쳐 움직인다 | 반일 단위 | 화면의 90%는 정적이고 10%만 살아 움직인다. **대부분의 외주 건에서 정답이다** |

**혼합 전략의 핵심**: 슬라이스 요소는 움직임이 끝나면 스크린샷 위의 실제 슬롯으로 반드시 돌아가야 한다. 대상 카드가 그리드 위에 떠 있는 채 레이아웃으로 내려앉지 않으면 관객은 즉시 「가짜」로 읽는다(shotcraft·type-and-filter, Q9 판례에서 이 때문에 파일을 거의 전부 다시 썼다).

혼합 경로의 5단계 작업:

1. 전체 페이지 2x 스크린샷을 바탕에 깔고 디바이스 프레임에 넣는다(웹 제품은 `browser_window.jsx`, 데스크톱 App은 `macos_window.jsx`)
2. 움직일 요소를 layout.json 좌표에 맞춰 투명 배경 슬라이스로 따낸다
3. 스크린샷 바탕에서 슬라이스가 있던 자리에 「페이지 배경색 패치」를 덮어 구워 박힌 원래 요소를 가린다(spotlight-hero-card의 제자리 패치 기법: 카드가 떠오른 뒤 원래 자리에 배경색 패치 + 강조색 호흡 테두리를 깔고, 착지 순간 밝아지며 사라진다)
4. 슬라이스를 패치 위에 겹쳐 애니메이션하고, 종점은 layout.json 슬롯으로 되돌린다
5. 클로즈업으로 밀고 들어가는 구간에서는 4x 고해상도 슬라이스를 6f 크로스페이드로 올려 낮은 배율 텍스처를 덮는다(shotcraft·PageCam 짝 기법)

**디바이스 프레임 선택**: 프레임은 「이것은 진짜 소프트웨어다」라는 맥락 신호다. 프레임 없는 스크린샷이 캔버스에 떠 있으면 스티커처럼 보인다. 다만 프레임도 화면 면적을 먹는다. 클로즈업이 zoom 2x를 넘어가면 프레임은 이미 화면 밖이므로, 그때는 프레임 없는 슬라이스를 그냥 써도 된다.

### 소재 3종 세트(경로 1·3으로 가기 전에 먼저 다 모은다)

shotcraft pipeline 1단계의 표준 수집물이다(shotcraft·6단계 pipeline).

| 소재 | 규격 | 용도 |
|---|---|---|
| 전체 페이지 2x 스크린샷 | 디바이스 픽셀 비율 2 이상, 긴 페이지는 전체를 한 장으로 | 바탕 텍스처. 줌인해도 흐려지지 않는 하한선 |
| 요소 투명 배경 슬라이스 | 따로 움직일 요소를 하나씩 따낸다. 4x면 더 좋다 | 혼합 경로의 「배우」. 클로즈업 구간에서 6f 크로스페이드로 낮은 배율 텍스처를 덮는다 |
| layout.json 좌표표 | 각 슬라이스의 전체 페이지 좌표계상 `{x,y,w,h}` | 움직임이 끝나고 돌아갈 「실제 슬롯」의 근거. 주석선·하이라이트 박스의 위치 기준점 |

스크린샷 출처는 `brand-asset-protocol.md`의 UI 스크린샷 수집 프로토콜을 따른다(App Store 스크린샷, 공식 사이트 screenshots, 시연 영상 프레임 캡처, 사용자 계정 실제 캡처). 품질 기준선도 「5-10-2-8」이 그대로 적용된다. 줌인 클로즈업에서 글자가 흐려지는 문제의 근본 해결책(transform scale 대신 CSS `zoom`으로 레이아웃 단위 확대)은 `camera-language.md`에 있다.

## §3 8식 상세

### ① 3D 전시대 / hero 클로즈업

핵심 오브젝트 하나(카드/패널/모듈)를 제품의 최소 단위로 세운다. 질감이 가장 높고 리듬이 가장 느린 컷이며, 오프닝 다음의 「단독 주인공 소개」 구간에 놓기 좋다.

| 파라미터 | 대표값 | 조절 감각 |
|---|---|---|
| 카메라 위치 | rotY 34°가 주도 + rotX는 8°만, perspective 1200px | 내려다보기보다 측면이 낫다. 「아래가 아니라 왼쪽에서 찍는다」. rotX가 커지면 책상을 내려다보는 그림이 된다 |
| 줌인 | 전체 페이지 zoom 0.78에서 한 박자 정지, 그다음 16f로 zoom 2.6까지 밀고 들어간다 | 밀기 전의 정지는 「관객에게 전체를 먼저 보여주는」 장치다. 바로 밀어 들어가면 공간감이 없다 |
| 동작 아크 | rise 10f(`cubic-bezier(0.2,1.25,0.3,1)` 오버슈트) → 정지 부양 54f(sin bob 진폭 4px, 주기 40f, translateZ 110px) → reseat 18f 착지, press scale 0.997 | 락온부터 착지까지 약 3.3s. 질감을 내는 컷은 이 정도로 느려야 한다. 첫 버전은 거의 항상 빠르다 |
| 윤곽 광선 | SVG rounded-rect 테두리를 두 바퀴 돌린다. 첫 바퀴는 14f로 빠르고 밝게, 둘째 바퀴는 20f로 느리고 약하게(opacity 0.62) | 두 바퀴의 빠르기가 달라야 「계속 스캔한다」로 읽힌다. 한 바퀴는 눈 깜빡임이다. 광선은 영상 전체에서 주인공에게 한 번만 준다 |
| 이중 그림자 | `0 8·lift px …, 0 46·lift px 90·lift px` — 부양 높이에 따라 자란다 | 그림자가 높이에 따라 자라지 않으면 부양이 성립하지 않는다 |
| 스포트라이트 유도 | 떠도는 빛이 중간 정차점 4곳을 거쳐 카드 중심에 락온한다. 광원 반경은 620→420→360으로 좁혀지고, 락온 순간 +6% 펄스. 외부 vignette은 0.16→0.42로 어두워진다 | 중간 정차점이 있어야 「무작위로 비추다가」가 믿긴다. 목표로 곧장 가면 프로그램된 것으로 읽힌다. vignette은 스포트라이트의 나머지 반이다 |
| 공중 주석(선택) | 카드 옆에 세리프 주석 두 줄이 떠오른다. translateZ 92px + bob 주기 44f(카드의 40f와 가깝지만 동기되지 않는다) | 거울처럼 동기시키는 게 아니라 「공감」이다. 주석은 같은 3D 공간, 같은 카메라 투시 안에 살아야 한다. 평면으로 글자를 올리면 공간의 통일성이 깨진다 |

(이상 전부 shotcraft·spotlight-hero-card 실측값)

알려진 함정: 마무리에서 「zoom 2.6→2.58」 같은 꼬리 드리프트는 금지다. 호흡은 진짜 정지여야 한다. 오프닝에 카드 여러 장이 군무를 하면 첫인상을 받쳐주지 못한다. 처음부터 단독 주인공 + 완결된 동작 아크로 시작한다. 카드마다 glint를 넣는 것은 판례에서 두 번 부결됐다. 광효과는 주인공에게만 엄격히 준다.

짝이 되는 카메라 워크: dolly-in 줌인 + 락온 후 정지 hold(`camera-language.md` 참고). 배율 폭이 2x를 넘으면 지속 시간을 로그로 늘리고, 스프링 오버슈트는 금지다(huarec).

### ② 화면 단계적 생성 build-up

화면이 「없던 상태에서 생겨나는」 등장 서사다. **build 순서에는 문법이 있다.** chrome(창 프레임/타이틀바) → 스켈레톤(회색 바 플레이스홀더) → 콘텐츠 블록 stagger → 데이터(숫자·차트가 마지막에 살아난다). 관객은 skeleton screen에 대해 공짜로 기대를 갖고 있다. 회색 바가 나오면 콘텐츠가 곧 온다는 것을 안다.

출처 카드 세 장은 대상에 따라 역할이 갈린다. **화면 하나**가 단계적으로 진짜가 되는 것은 skeleton-reveal, **행·카드 묶음**이 리스트에 끼워지는 것은 row-embed, **문서 한 편**이 쓰여 나가는 것은 document-typewriter-reveal이다.

| 파라미터 | 대표값 | 조절 감각 |
|---|---|---|
| 3단 현상 | 낙서(5f마다 시드를 바꿔 「끓게」 만든다) → 실물로 바뀌는 한 박자에 8f로 가속 축소·후퇴 + 스켈레톤 spring 진입 → 스켈레톤 행이 6f 시차로 굴러 들어옴 → 현상되는 행은 13f 시차, 행 안에서는 12f | 실물로 바뀌는 한 박자는 빠르고 단호해야 한다. 길게 끌어 crossfade가 되면 「도약」이 사라진다. 3단의 레이아웃은 엄격히 같은 구조여야 하고, 어긋나면 페이지가 바뀐 것으로 읽힌다 |
| 단어 단위 등장 | 단어당 2.5f, 14px 위로 떠오른다. 마지막 행의 마지막 단어는 +14f로 반 박자 늦는다 | 반 박자 늦는 것이 「로딩 완료」의 마침표다. 전부 동시에 떨어지면 평범해진다 |
| 행 삽입 | i번째 행의 cue = 12 + i·9, 비행 12f. `perspective(900px) translateY(−120·air) rotateX(16°·air)` | **rotateX가 평평해지는 것이 「끼워 넣기」로 읽히는 핵심**이다. translateY만 쓰면 그냥 「떨어짐」이다 |
| 삽입 강조선 | 아래변 2px 강조색 선이 중심에서 5f에 걸쳐 펼쳐지고 8f에 사라진다 | 삽입마다 확인점을 하나 주되, 빨리 사라져야 한다 |
| 문서 블록 단위 | g번째 블록의 cue = 6 + g·3.5, 블록마다 wipe 8f. 강조색 caret은 가장 최근 블록만 따라간다 | **「블록 수 × 박자를 먼저 예산에 맞춘다」가 핵심 산수**다. 블록이 많으면 속도를 올리지 말고 블록을 줄인다. 「펜촉은 언제나 하나뿐이다」 — caret 두 개가 동시에 깜빡이면 저자가 두 명인 것이다 |

(skeleton-reveal / row-embed / document-typewriter-reveal 세 카드의 실측값)

알려진 함정: 실제 콘텐츠 층에 제품 스크린샷을 붙일 때는 스켈레톤 회색 바의 행 높이와 슬롯을 스크린샷에서 재서 맞춘다. 상상으로 배치하지 않는다. 낙서 단계에서는 디테일을 그리지 않는다. UI와 너무 비슷하면 1단과 2단의 차이가 없어진다. 목업 문안에는 고객사·구성원의 실명을 쓰지 않는다.

짝이 되는 카메라 워크: 현상 구간에는 1→1.34 느린 줌인을 붙인다(「가까이 가서 똑똑히 본다」는 시선 동기를 준다). build 내내 카메라 횡이동은 넣지 않는다. 화면이 변하는 동안 카메라는 안정적이어야 한다(huarec: 전체 화면 단위 변화에는 줌을 걸지 않는다).

### ③ 사용자 typing 시뮬레이션

사람이 입력창·터미널에 타이핑하는 모습을 시뮬레이션한다. 기존의 **Chunk Reveal(AI 스트리밍 출력)과는 완전히 다른 것**이다. AI 출력은 불규칙한 chunk가 몰려 나오는 것이고(best-practices §4.5, gsap-recipes §3.4 — 그쪽은 그대로 쓰고 여기서 다시 쓰지 않는다), 사용자 입력은 한 글자씩, 고르게, 망설임이 섞인 사람 손의 리듬이다. 이 둘을 혼동하는 사고가 자주 난다. 사용자 타이핑을 chunk로 만들면 「입력창이 스스로 생성하고 있다」로 읽힌다.

| 파라미터 | 대표값 | 조절 감각 |
|---|---|---|
| 타이핑 속도 | 본문 3f/글자, 터미널 2f/글자, 장식용 작은 글자 0.7f/글자 | 「첫 버전이 빠르다고 퇴짜 맞고 다시 잡은 확정값」이다. 인터랙션 시연은 사람의 조작 속도를 따른다. 판례급 철칙이다 |
| 커서 상태 기계 | 타이핑 중에는 **상시 점등**, 다 치면 8f 주기 깜빡임으로 바뀐다 | 타이핑 중에 깜빡이면 버벅임으로 읽힌다. 상시 점등 → 깜빡임 전환 자체가 「다 쳤다」는 신호다 |
| 백스페이스 수정 | 어쩌다 한 번. 1-2글자를 더 치고, 4-6f 멈추고, 지우고, 다시 제대로 친다 | 「사람은 틀린다」가 가장 싼 리얼리티다. 다만 스크립트에 미리 써 넣어야 한다(프레임 결정성). 런타임 난수가 아니다 |
| 확인 정지 | 타이핑 완료부터 페이지 반응까지 11f(0.37s) 호흡을 둔다 | 다 치자마자 반응하면 기계 자동화로 읽히고, 관객이 인과를 따라가지 못한다 |
| 코드 타이핑 | 터미널 2f/글자. 문법 하이라이트는 타이핑과 함께 점진적으로 색이 입혀진다(현재 token을 다 치면 바로 착색). 한 단락을 다 치고 한꺼번에 색을 바꾸지 않는다 | 한꺼번에 색이 바뀌면 「붙여넣기」이고 「코드 작성」이 아니다. 하이라이트 지연이 token 반 개 안이면 관객은 알아채지 못한다 |
| 스크린샷 위에서 타이핑 | 배경색 패치로 스크린샷에 구워 박힌 placeholder를 덮고(아이콘은 남긴다), 텍스트 층을 위에 겹쳐 타이핑한다 | 글자를 그냥 겹치면 구워 박힌 placeholder와 겹쳐 보인다 |

(shotcraft·type-and-filter 실측값)

백스페이스 수정의 결정적 구현(미리 쓴 스크립트이고, 런타임 추첨이 아니다):

```js
// 「틀림 → 멈춤 → 지움 → 수정」을 문자 이벤트 표로 컴파일한다. 타임라인은 그것을 재생만 한다
const script = typeScript("nano-lab", {
  perChar: 3 / 30,                       // 3f/글자
  typo: { at: 5, wrong: "0", pauseF: 5 } // 5번째 글자에서 "0"을 잘못 치고, 5f 멈춘 뒤 지운다
});
// script = [{t:0, text:"n"}, {t:0.1, text:"na"}, ... {t, text:"nano-0"},
//           {t+0.17, text:"nano-"}, {t+0.27, text:"nano-l"}, ...]
// 렌더 층은 t로 표를 찾아 text를 가져온다. 양방향 seek에 안전하다
```

짝이 되는 카메라 워크: 타이핑 전에 카메라를 먼저 입력창으로 올리거나 밀어 넣는다(먼저 화면을 주고 그다음에 손을 움직인다 — 가시성 공리). 타이핑 중에는 카메라를 완전히 고정한다.

### ④ 커서 조작 서사

커서는 UI 시연에서 유일한 「사람」이다. 컴포넌트는 `assets/cursor.jsx`를 쓴다(CursorSprite / ClickRipple / hover 연동 hook, 두 가지 시계 구동, API는 해당 파일 상단 주석 참고).

궤적 알고리즘은 여기서 다시 쓰지 않는다. 베지어 호선 + 수렴하는 손떨림은 best-practices §3.5, GSAP proxy 구현은 gsap-recipes §3.5를 본다. 이 식에서 채우는 것은 **클릭과 연동의 파라미터**다.

| 파라미터 | 대표값 | 조절 감각 |
|---|---|---|
| 이중 원 ripple | 동심원 두 개, **시작점 차이 3f**, 반경 14→54 / 14→78px | 원 하나는 너무 가벼워 보이지 않는다. 3f 차이가 「한 번 클릭의 파문」이고, 더 벌어지면 두 번 클릭한 것처럼 보인다 |
| 확산/소멸 분리 | 확산은 out-cubic 22f, 소멸은 선형 26f | 확산은 치고 나가야 하고 소멸은 고르게 빠져야 한다. 한 곡선으로 두 가지를 처리하면 「한 번 반짝하고 없어진다」. 촘촘한 장면에서는 각각 10f까지 줄일 수 있다(type-and-filter가 쓰는 것이 이 압축 버전이다) |
| 클릭 준비 동작 | 커서 scale 0.85(power1.in, 약 3f) → back.out으로 되돌아온다 | Anticipation이 클릭에 「눌렀다」는 무게를 준다(gsap-recipes §3.5와 같은 것) |
| hover 연동 | 커서가 대상 영역에 들어오면 같은 프레임에 대상이 밝아진다(brightness +6% 또는 hairline 테두리가 떠오른다). 커서가 떠나면 즉시 걷힌다 | 대상이 반응하지 않으면 커서는 그냥 스티커다. 연동 구간은 궤적 진행률로 선언하고, 런타임 히트 판정은 하지 않는다 |
| 커서의 역할 분담 | 조작 커서(클릭에 payload가 있다) vs 연기 커서(이동 자체가 이야기다. 이름 붙은 협업 커서의 2인무·군무) | 커서가 무언가를 클릭해야 할 때는 이 식을 쓴다. 순수하게 서사만 하는 협업 커서는 다른 장면이다(shotcraft·collab-cursor-moves). 한 편에 함께 있을 수는 있지만 섞지 않는다 |

연기 커서 두 가지 빠른 참조(협업·다인 주제일 때 쓴다. 파라미터는 collab-cursor-moves에서 나왔다):

| 식 | 메커니즘 | 핵심 파라미터 |
|---|---|---|
| dialogue-duet 2인무 | 파랑·초록 이름 붙은 커서 두 개가 가까워져 대화하고, 위아래로 호를 나눠 자리를 바꾼다(R≈270px). 이름표가 하나는 밝아지고 하나는 어두워지며 조명이 넘어간다. 초록 커서는 easeIn으로 수십 배 확대되어 전환용 차폐가 된다 | 전부 3차 베지어 이동이고 linear는 없다. 두 개가 같은 호를 같은 방향으로 가면 부딪히는 느낌이 나므로, 위아래로 호를 나누는 것이 「양보」다 |
| cast-ensemble 군무 | 색색의 커서 5개가 delay 0/5/9/13/17f 시차로 spring을 타고 날아 들어온다. 두 주파수 사인 드리프트로 자리를 잡고(0.055/0.021 rad/f, 진폭 ±46/30px), 그중 하나가 타이핑 카메오를 한다 | 이름표가 12f 늦게 페이드인해야 「도착한 다음 스스로 이름을 밝히는」 것이 된다. 모인 뒤 드리프트는 25%까지 감쇠시켜 남긴다. 완전히 정지한 커서 무리는 먹통으로 읽힌다 |

알려진 함정: 커서 이동은 전 구간에서 가시성 공리를 지켜야 한다. 대상이 화면 밖이면 카메라를 먼저 움직인 다음 커서를 움직인다. 협업 커서의 이름표 색은 신원 코드다. 영상 전체에서 일관되어야 하고, 중간에 색을 바꾸면 관객은 사람이 바뀐 줄 안다. 드리프트하는 커서는 지금 읽히고 있는 주 콘텐츠를 절대 가려서는 안 된다.

짝이 되는 카메라 워크: 클릭이 확인된 뒤 카메라가 16f 동안 밀고 들어가(zoom≈2.2) 상세 페이지로 관통하는 것이 「클릭 → 진입」의 표준 바통 넘김이다(type-and-filter). 전환을 이어 붙이는 방법은 `camera-language.md`를 본다.

### ⑤ UI 상태 전환의 타임라인화

tab 전환, modal 팝업, 페이지 라우팅 진입. **타임라인이 구동하는 재생과 인터랙티브 프로토타입은 서로 다른 두 가지 코드 형태**다. 프로토타입을 렌더용으로 고칠 때 항목별로 옮긴다.

| | 인터랙티브 프로토타입 | 타임라인 재생(렌더용) |
|---|---|---|
| 트리거 | `addEventListener('click')` | timeline의 label / position 파라미터 |
| 상태 전환 | `classList.add` + CSS transition | 명시적 tween(gsap-recipes §6.1 금지 구역 규칙) |
| 열기/닫기 | `display: none` 토글 | `autoAlpha` tween |
| hover | `:hover` 가상 클래스 | 궤적 진행률로 선언한 연동 구간(8식 ④) |
| 난수 | `Math.random()` | mulberry32 시드로 미리 생성(gsap-recipes §6.4) |

고친 뒤 `grep "addEventListener\|classList\|transition:"`로 하나씩 0이 될 때까지 정리한다. 상태는 시간의 순수 함수여야 한다. preview에서는 정상인데 렌더에서만 티가 나는 버그는 전부 여기서 나온다.

| 파라미터 | 대표값 | 조절 감각 |
|---|---|---|
| modal / 커맨드 팔레트 | 배경을 10f 동안 rgba(20,20,20,0.45)까지 어둡게 + blur 10px. 패널은 −20px → +8px 오버슈트(9f) → 제자리(6f). 후보 행은 i·4f 시차 | 배경을 어둡게 하지 않으면 패널이 「위에 떠 있는」 느낌이 없다. 오버슈트 8px가 「가볍게 내려앉음」이고, 더 크면 장난감이 된다 |
| tab 전환 | 인디케이터 바는 FLIP으로 미끄러진다(best-practices §4.1). 기존 콘텐츠는 5f 동안 페이드아웃하며 8px 가라앉고, 새 콘텐츠는 8f 동안 페이드인하며 떠오른다 | 인디케이터와 콘텐츠가 서로 맞지 않으면 싸구려로 읽힌다. 맞추는 방식은 바가 먼저 가고 콘텐츠가 반 박자 따라오는 것이다 |
| 라우팅 진입 | 새 페이지가 오른쪽에서 전체 화면으로 12-16f에 걸쳐 밀려 들어오고, 기존 페이지는 같은 방향으로 30% 거리만 물러나며 어두워진다 | 기존 페이지가 짧게 물러나면(시차) 같은 거리로 밀리는 것보다 깊게 읽힌다. 같은 거리는 「컨베이어 벨트」다 |

(modal 파라미터는 shotcraft·command-palette-summon 실측값이다)

알려진 함정: 상태 전환은 「한 컷에 하나의 모션」이 가장 자주 깨지는 자리다. 한 번의 전환에서 tab도 바뀌고 toast도 뜨고 데이터도 굴러가면 관객은 아무것도 보지 못한다. 한 컷에서는 상태 변화를 한 번만 연기한다.

짝이 되는 카메라 워크: 상태가 바뀌는 순간 카메라는 반드시 정지해 있어야 하고, 전환이 끝난 뒤에 움직인다(huarec 컷 간 문법: 변화는 주의력 소비다. 카메라 운동과 겹쳐서 소비시키지 않는다).

### ⑥ 화면 3D 투어

긴 화면이나 여러 화면의 「공간감」을 보여주는 컷이다. 두 카드의 역할이 분명하고, 카드를 잘못 고르는 것이 이 식의 주된 사고다.

| 카드 | 메커니즘 | 적용 |
|---|---|---|
| steep-tilt-glide | **카메라 정지, 페이지 이동**: 페이지를 rotateY −60°로 기울여 놓고, 페이지가 일정한 속도로 화면을 지나간다 | 페이지를 「전시품」처럼 줄지어 지나가게 할 때. 내용을 읽힐 필요는 없고, 보여주는 것은 규모와 질감이다 |
| graze-face-tour | **카메라 이동, 페이지 정지**: 페이지 무리가 공중에 떠서 고정되고, 카메라가 화면에 바짝 붙어 훑는다 | 투어 중에 일부 내용을 읽혀야 할 때. 카메라에 「관람객」이라는 인격이 있다 |

| 파라미터 | 대표값 | 조절 감각 |
|---|---|---|
| 기울임 각 | rotateY −60°, 실전 판정 구간은 55-65° | −45°는 「덜 기울었다」고 판정됐고, −70°를 넘으면 내용을 읽을 수 없다 |
| 부양 높이 | 120-180px(graze-face-tour) | 낮으면 바닥에 붙어 「진열」 느낌이 없고, 높으면 그림자와의 연결이 끊긴다 |
| 무리의 시차 | 시작점은 어긋내되 하강은 겹쳐서 병행시킨다 | 완전히 순서대로 떨어지면 「줄 서서 출석 체크」이고, 겹쳐야 「한 무리가 도착」이다 |
| 구간 연결 | 크로스페이드 ≥8f | 하드 컷은 검은 플래시를 만든다. 투어는 연속된 공간이므로 점프 컷은 금지다 |

(shotcraft·steep-tilt-glide / graze-face-tour 실측값)

여러 페이지를 한 화면에 진열하는 세 번째 변형(shotcraft·page-waterfall-wall): 3열 페이지 폭포 벽, rotateX 20° + perspective 1000px, 인접 열의 loop 주기 차이는 ≥25%(예: 12/9/14s)이고 가운데 열은 방향을 뒤집는다. 마무리 구간에서 「제품에 페이지가 많다」는 규모를 진술할 때 알맞고, 내용을 읽힐 필요는 없다. 주기 차이가 25%보다 작으면 세 열이 주기적으로 정렬되고, 그 순간 「벽」이 「표」로 바뀐다.

알려진 함정: 두 카드의 메커니즘을 섞어 쓰면 안 된다. 페이지와 카메라가 동시에 움직이면 관객은 기준계를 잃는다(어지럽다). 투어에 쓰는 페이지 텍스처는 2x 이상이어야 한다. 기울여 확대하면 가장 빨리 흐려진다.

짝이 되는 카메라 워크: 이 식 자체가 카메라 워크의 주인공이므로 앞뒤 컷은 정적이어야 한다(에너지 교대). 카메라 경로와 orbit 어휘는 `camera-language.md`를 본다.

### ⑦ 긴 페이지 스크롤 서사

긴 랜딩 페이지·문서·타임라인의 「빠른 스크롤과 급제동」이다. 스크롤 자체는 콘텐츠가 아니고, **제동점이 콘텐츠다**.

| 파라미터 | 대표값 | 조절 감각 |
|---|---|---|
| 제동 곡선 | `Easing.out(Easing.exp)` 한 곡선으로 50f에 전 구간을 소화한다 | 구간을 나눠 감속하면 「펌프질」처럼 된다. expo 곡선 하나가 그대로 「세게 굴러가다 서서히 멈춤」이다 |
| 모션 블러 | blur는 프레임 간 이동량 차분으로 구동한다. 속도가 크면 흐려지고 멈추면 선명해진다 | 일정한 blur는 「렌즈가 더러운」 것이다. 움직이는 순간에만 블러가 있고 정지 프레임은 항상 선명하다(huarec도 같은 결론) |
| 목표 행 강조 | 멈춘 뒤 목표 행은 scale 1.03, 나머지는 0.38까지 어두워진다 | 어둡게 하되 0까지 가지 않는다. 문맥은 남아 있어야 한다. 1.03은 「호흡」이지 「튀어나옴」이 아니다 |

(shotcraft·scroll-brake-moves 실측값)

제동점이 여러 개일 때의 예산 관리(huarec 편안함 예산을 그대로 가져왔다): 인접한 두 번의 「스크롤+제동」 간격은 ≥2.6-3.0s, 임의의 15s 구간 안에 ≤4-5회, 각 제동점에서 ≥1.2s 머문 뒤 다시 굴린다. 제동점은 주의력 소비이고 스크롤 자체보다 비싸다.

알려진 함정: 스크롤 중 줌인은 금지다. 「스크롤 중에 밀고 들어가면 어지럽다」(huarec: 전체 화면 단위 변화에는 카메라를 밀지 않는다). 제동점에 콘텐츠 강조가 없으면(목표 행이 올라오지 않고 나머지가 어두워지지 않으면) 관객은 왜 여기서 멈췄는지 모른다.

짝이 되는 카메라 워크: 급제동 뒤에 목표 행으로 가벼운 줌인(1.3x 단)을 한 번 붙일 수 있지만, 완전히 멈춘 다음이어야 한다. 단계표는 `camera-language.md`에 있다.

### ⑧ feature callout 주석

실제 스크린샷 위에서 「관객에게 가리켜 보여주는」 것이다. 하위 레시피는 네 개이고, 공통 원칙은 하나다. **주석은 안내원이고 인터페이스의 일부가 아니다.** 스타일은 제품 UI와 한 겹 벌려야 한다(세리프 글자/손글씨 느낌/강조색).

| 하위 레시피 | 파라미터 | 조절 감각 |
|---|---|---|
| 주석선 성장 | SVG 경로를 stroke-dashoffset으로 그린다. 12-18f, out-cubic. 선이 먼저, 글자는 나중 — 선이 도착한 뒤 5f에 걸쳐 페이드인 | 선과 글자가 같이 나오면 스티커로 읽힌다. 선은 「손가락이 훑고 지나가는」 시간이다 |
| 하이라이트 박스 | 대상 영역에 rounded-rect 테두리가 8f 동안 펼쳐지고, 박스 밖은 0.3까지 어두워진다 | 테두리만 그리고 밖을 어둡게 하지 않으면 시선이 모이지 않는다. 0.5를 넘게 어둡게 하면 취조실 조명이 된다 |
| 확대경 | 원형 loupe 안에 2-3x 고해상도 슬라이스를 넣는다(스크린샷 바탕을 CSS로 확대하는 것이 아니다). 테두리 2px + 부드러운 그림자, 8f 오버슈트로 튀어나오고, 대상을 10-14f에 걸쳐 느리게 따라간다 | loupe 안은 반드시 고해상도 슬라이스여야 한다. 흐린 텍스처를 확대하는 것은 소재가 나쁘다고 스스로 폭로하는 것이다. 한 컷에 loupe는 최대 하나다 |
| 연결선 설명 카드 | 설명 카드가 3D 공간에 떠 있다. translateZ는 90px 수준, bob 주기는 본체와 가깝지만 동기되지 않는다 | 같은 3D 공간, 같은 카메라다. 평면으로 글자를 올리는 것은 판례에서 부결됐다(spotlight-hero-card 공중 주석과 같은 제약) |
| before/after slider | 빠른 스윙 12f(out-cubic 8%→76%, 오버슈트 후 70%로 되돌아온다) → 18f 정지 → 느린 스윕 48f로 40%에서 정지 프레임. 속도비 5:1. after 층의 clip-path가 손잡이를 따라간다. 손잡이 속도 차분이 scaleX 미세 신축을 구동하고 최댓값은 1.18 | 속도비가 3:1보다 작으면 리듬 대비가 느껴지지 않는다. 빠른 스윙은 「바뀌었다」를 선언하고, 느린 스윕은 「어디가 바뀌었는지」를 증명한다. 느린 스윕을 40%에서 멈추면 after가 정지 프레임에 남는다 |

(slider는 shotcraft·before-after-slider-scrub 실측값)

알려진 함정: before/after 두 버전은 같은 레이아웃, 같은 카메라 위치여야 한다. 아니면 서로 다른 두 페이지로 읽힌다. before는 실제 과거 상태를 쓴다(옛 데이터를 넣거나 기능을 끈다). 「일부러 못생긴」 가짜 before를 손으로 만들지 않는다. 코너 라벨은 콘텐츠 영역에 두고, 사이드바 프로필 사진을 덮지 않는다.

## §4 리듬 철칙(shotcraft 판례에서 계승, UI 시연 전용)

1. **인터랙션 시연은 사람의 조작 속도로 간다.** 타이핑 3f/글자, 클릭 전에 이동, 반응 전에 호흡. 인터랙션 컷의 첫 버전은 거의 항상 빠르다. 처음부터 사람 속도로 잡는다(판례 R3. type-and-filter가 이 때문에 재작업했다).
2. **여러 요소가 함께 움직인 뒤에는 0.5s 정지한다.** 그리드가 수렴하고, 리스트가 다 끼워지고, 패널이 다 내려앉으면, 화면 전체를 반 초 정지시킨 다음 다음 컷으로 간다.
3. **퇴장은 반드시 시차를 둔다.** 목표가 아닌 요소는 읽는 순서대로 0.4f 간격으로 시차를 두고 사라진다. 「동시에 사라지면 페이지가 죽은 것으로 읽힌다」. 0.4f 차이만으로도 충분하다(type-and-filter).
4. **한 컷에 하나의 모션.** 한 컷은 UI 동작 하나만 말한다. 같은 화면의 모션 두 개는 서로 장면을 빼앗고, 관객은 둘 다 보지 못한다.
5. **마무리는 진짜 정지다.** 호흡 자리와 hold 프레임에서는 어떤 꼬리 드리프트도 금지다(zoom 미세 변화, opacity 미세 조정도 포함된다). 「정지」는 설계된 한 박자이고, 동작을 못 넣어서 비워둔 자리가 아니다.

## §5 삼방향 게이트 · 자산 프로토콜과의 접점

**삼방향 보드를 어떻게 내는가**: 제품 UI 애니메이션의 삼방향은 시각 스킨 세 벌이 아니라 **같은 UI 소재를 카메라 서사로 세 가지로 해석한 것**이다. 소재 3종 세트는 한 번만 모으고 세 방향이 함께 쓴다. 예를 들어 같은 제품 스크린샷 한 장으로, 방향 A는 8식 ①(단독 주인공 hero 클로즈업으로 소개), 방향 B는 8식 ②(build-up으로 없던 것이 생겨나는 생성 능력을 말한다), 방향 C는 8식 ⑥+⑦(투어+스크롤 서사로 규모를 말한다)로 간다. 각 방향 보드에는 키프레임 thumbnail 2-3장을 붙여, Neo가 고르는 것이 「이 화면을 어떻게 이야기할지」가 되게 한다. 「어느 그림이 예쁜지」가 아니다. 삼방향 게이트는 100% 강제 게이트이고, 스타일을 지정해도 면제되지 않는다(SKILL.md의 기존 규칙).

**UI 스크린샷 수집은**`brand-asset-protocol.md`를 따른다**: 디지털 제품의 UI 스크린샷은 그 프로토콜에서 1등 시민 자산이다(식별도 기여가 매우 크다). 수집 채널, 5-10-2-8 품질 기준선, brand-spec.md 고정까지 전부 그대로 따른다. 이 문서가 더하는 것은 한 가지뿐이다. 수집할 때 §1의 소재 3종 세트 규격대로 한다(2x 전체 페이지 + 투명 배경 슬라이스 + layout.json). 한 번에 다 모아 두면 카메라 워크와 재구축 두 경로 모두에 충분하다.

**가짜 UI를 손으로 만드는 것은 금지**: 실제 스크린샷을 찾을 수 없으면 프로토콜의 폴백을 따른다(사용자에게 실제 캡처를 요청하거나 공식 시연 영상에서 프레임을 캡처한다). 목업 생성기로 때우지 않고, CSS로 「그럴싸한」 화면을 그리지 않는다. 우리가 표현하는 것은 이 제품이고, 「어떤 제품 하나」가 아니다.

**예외는 하나뿐이다**: 경로 2 HTML 재구축으로 갔다면, 재구축본 자체가 「실제 스크린샷을 기준으로 한 복제」다. 스크린샷과 대조해 블록별로 검증해야 하고(글꼴, 라운딩, 여백, 아이콘을 전부 스크린샷에서 잰다), 재구축이 끝나면 스크린샷과 나란히 놓고 프레임을 비교한다. 「대충 비슷한」 화면을 만드는 것은 스크린샷을 그대로 쓰는 것보다 해롭다. 관객은 자기가 매일 쓰는 제품 화면의 오차에 극도로 민감하다.

- [ ] 여러 요소의 퇴장이 ≥0.4f 시차를 두고, 마무리에 화면 전체가 0.5s 정지하는가?
- [ ] 윤곽 광선·glint를 쓴 컷이 영상 전체에서 하나뿐이고, 주인공에게만 주었는가?
- [ ] before/after가 같은 레이아웃, 같은 카메라 위치이고, before가 실제 과거 상태인가?
- [ ] 삼방향 보드가 같은 UI 소재의 세 가지 카메라 해석이고, 스킨 세 벌이 아닌가?
